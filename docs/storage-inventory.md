# Storage audit and SQLite migration record

This inventory is based on the current source paths and active call sites. The
authoritative structured application store is now the SQLite database created
by the Go engine. Legacy JSON/localStorage sources are retained only for
explicit, verified import or installation-local UI state.

| Data | Previous source and access path | Current authority | Migration / compatibility |
|---|---|---|---|
| Users and profiles | `data/users.json`, `routes_auth_data.go` | SQLite `users`, owner resources | Credential-verified import; legacy password hashes are upgraded after login |
| Browser sessions | `data/auth_sessions.json` | SQLite session table with SHA-256 token hashes | Expired/revoked sessions are not imported as usable tokens |
| Provider metadata/secrets | `data/providers.json`, `routes_providers.go` | SQLite owner-scoped provider records plus `SecretStore` | Secret-free API responses; existing JSON remains for explicit migration/rotation |
| API keys | Previous local/Supabase API-key records | SQLite hashed external keys | New keys are generated by Go and revealed once; raw keys are not imported |
| Usage logs | Supabase `api_usage_logs` / local resource records | SQLite owner-scoped usage resource | API gateway writes records through the Go backend |
| MCP servers and headers | `data/mcp_servers.json`, Supabase MCP table | SQLite owner-scoped records with encrypted headers; portable `mcp/` registry/config files | Registered IDs are required for proxy calls; SSRF checks remain server-side; credential files contain references only |
| Knowledge documents and RAG chunks | Supabase documents or local backend resource | SQLite owner-scoped `rag_documents` and `rag_chunks` | Embedding provider is explicit; unavailable providers fail closed |
| Agent runs/events/checkpoints | In-memory store and `data/agent-runs/*.json` | SQLite `agent_runs`, `run_events`, `run_checkpoints` | Transactional import with backup, checksum marker, and explicit owner map |
| Tool execution lifecycle | Response-local tool logs | SQLite `tool_calls` plus portable `toolcalls/history`, `results`, `artifacts` | SQLite is canonical; Go validates arguments, enforces timeout/cancellation, redacts secrets, and stores large outputs separately |
| Chat conversations | Zustand `localStorage` | SQLite `/v1/conversations/state` | Explicit user-confirmed import with stable source ID; legacy source is not deleted |
| Settings | Zustand/localStorage and provider preference JSON | SQLite `/v1/settings/user` | Account-scoped state hydration; pending UI outbox is transient and owner-namespaced |
| Download progress/theme/layout | Browser localStorage | Installation-local UI state | Not account authority; safe to retain locally |
| Model weights/artifacts | Filesystem configured by engine | Filesystem outside SQLite | SQLite stores metadata only; paths are validated by the backend |
| Secrets/tunnel credentials | Environment/OS credential manager | OS credential manager or externally provisioned encryption key | Never stored beside SQLite ciphertext or returned to renderer |

## Database location and guarantees

The default database is:

```text
<portable root>/db/studio.sqlite
```

The Go application resolves portable data paths before opening SQLite.
`AI_SERVER_DATA_DIR` is useful for controlled deployments and tests only when it
is contained by `AIST_PORTABLE_ROOT`.

The database uses WAL, `synchronous=FULL`, foreign keys, a 10-second busy
timeout, a single application connection, transactional migrations, integrity
checks on startup, and private file permissions. Backups use `VACUUM INTO` and
never overwrite an existing destination.

## Legacy import safety

Imports are not assigned to the first account that logs in. Agent-run import
requires `AI_SERVER_AGENT_RUN_OWNER_MAP`, which maps each legacy run ID to a
known SQLite user ID. Ambiguous or unowned records are skipped and reported.
Original files remain in place after a verified import, and a private backup
is created before mutation. Frontend chat import requires explicit user
confirmation and an idempotent source ID.

## Known limitations

- SQLite account isolation protects application behavior, not an attacker with
  full operating-system access to the user profile and OS credential store.
- Semantic RAG requires an injected embedding provider. The service reports an
  unavailable capability instead of returning simulated vector results.
- JSON files in the repository are migration inputs/reference artifacts, not
  the runtime authority after the first successful SQLite initialization.
